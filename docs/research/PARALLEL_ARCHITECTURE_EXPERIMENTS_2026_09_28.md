# Parallel architecture experiment screens — 28 September 2026

This report follows the [project architecture review](ARCHITECTURE_NOVELTY_REVIEW_2026_09_28.md) and the completed agent's [engine profile and routed prototype](/Users/sayat/.codex/worktrees/21f0/tinyML_accelerator/docs/research/PHASE_6_ENGINE_PROFILE_AND_PROTOTYPE_V1.md). Its purpose is to reject weak novelty hypotheses before a larger RTL campaign. The six screens below use different evidence levels; modeled traffic and service are never presented as device latency.

The strongest available *measured* KWS/VWW reference is generic B3 on the 27 MHz cached-weight co-issue image: **1,119,142 KWS and 2,157,255 VWW device cycles**, with exact short-screen outputs. That is a 6.889% geometric-mean latency reduction versus generic B3 on the predecessor image in separate protocol-matched sessions. The route uses 10,090/10,368 CLS and 38/46 BSRAM blocks. Those results belong to the completed task; this report does not repeat its board campaign or claim accuracy-set or energy qualification for that image.

## AD provenance and the memory incident

The AD experiment uses all **21,952 calibration windows** and all **48,608 disjoint evaluation windows** from the pinned ToyCar archive. A window is a five-frame, 640-feature inference; each of 248 recording scores averages 196 window reconstruction errors. The float result exactly reproduces the frozen source-quality score. The software VM image is 3,168,320 bytes because it embeds calibration provenance; its separate FPGA-lowering parameter image is 292,368 bytes. Native reports pin both executables to passed source/build reports. The candidate's KWS/VWW cache-hit gain does not transfer to this held-out dense graph under the same AD command stream.

The initial AD calibration process caused the reported >40 GB growth. In `compiler/static_cli.py`, `data[name][i]` was inside a 21,952-sample comprehension. Each access decompressed the **entire ~56 MB NPZ array**, and each row view retained that new backing array. [The fix](../../compiler/static_cli.py) loads each input member once and yields views; a [regression test](../../compiler/test_static_cli.py) checks shared storage. Full calibration now completes in about 10 seconds with **157.4 MiB measured peak RSS** and reproduces the same image hash. The CLI/static-pipeline test selection passes **59/59** tests.

## Research decision

The original review's leading thesis, *exact quantized fusion under a joint control, tensor-state, and memory-port budget*, has **not** survived its first strong controls on these models. A blocked quantized producer tile avoids the proposed continuation's INT32 read/write traffic, and the useful control-memory block saving is explained by a fixed partition. Narrow context storage is conditional on a context memory that the current engine does not have. None of the modeled savings should be added to the existing 27 MHz board medians.

The most concrete next hardware control is a **two-output activation-stationary pointwise loop order** implemented with the same eight MAC lanes, memory ports, and physical block budget, then checked and routed alongside the current co-issue image. This is a baseline strengthening step. A research contribution would need a mechanism that still wins after that control, fixed program/data partitioning, ordinary blocked fusion, and adapted published fusion schedules, including held-out AD and a residual graph. Report exact full-model correctness, routed frequency and area, matched board latency, and energy before claiming a top-tier architecture result. The current experiments provide a reproducible negative/conditional decision, not that result.
